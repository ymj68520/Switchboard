## Gate 2 — Live semantic validator (RR-03, closure brief §28–§32)

**Status: EXECUTED ×3 FULL RUNS (9 recorded validator attempts) — BLOCKED BY PROVIDER POLICY, not throttling, not product. Root cause established by direct evidence and bisection.**

The committed script (`npm run smoke:opencode-validator`, fixed this run — see below) drives: real session → TEST-ONLY setup to synthesis/manifest-ready (zero model turns) → REAL `OpenCodeSemanticValidator` over a real SDK client → real model → strict parser → ephemeral session cleanup. Every run reached the validator correctly; every real inference was refused by the provider with an EMPTY assistant reply; the adapter failed closed each time (`validation_output_invalid: output is empty`, 9/9 attempts recorded, no fake output injected).

**Evidence chain (all from 2026-09-28, provider otherwise healthy — context smoke 17/17, main smoke 37/37, journey 14/14, handoff-det 19/19 all green the same morning):**

1. Host process log (authoritative): every validator attempt logs
   `AI_APICallError: Error from provider (Console): OpenCode's free tier can only be used from within OpenCode` (`stream error … agent=build mode=primary`), followed by the adapter's ephemeral-session deletion.
2. Bisection with the EXACT adapter request shape (SDK `session.prompt`, `body.system` = `SEMANTIC_VALIDATION_SYSTEM_PROMPT`, real capsule sizes to 11,942 chars):
   - without `body.tools` → **success** (full text replies, repeatedly);
   - with the validator's 34-name tools-disable map → **0 parts** (the exact failure);
   - with a minimal map `{bash: false}` → **0 parts** — ANY per-request tools map triggers the refusal;
   - on alternative free-tier models (`nemotron-3.5-lightning-free`, `space-bunny-free`) → **0 parts** — provider-wide across the validated free tier.
3. Conclusion: the free-tier Console provider refuses ANY model request that carries a per-request `tools` map — an anti-abuse fingerprint. The frozen validator design (§8/§9 structural tool isolation) REQUIRES that map, so the real-validator gate is architecturally unreachable on the entire validated free-tier provider. This is a provider policy boundary, NOT rate limiting (yesterday's separate 429 window produced the same empty-reply symptom through real throttling) and NOT a product defect (the adapter, parser, and fail-closed behavior did exactly what the frozen architecture specifies; the deterministic suite proves them).

**Harness fix applied this run (test-only, committed `efb41a4`):** the smoke spawned its servers with `--print-logs` but never drained the pipes; an undrained 64 KB pipe buffer blocks the OpenCode server mid-turn on Windows and also surfaces as zero-part replies. The det and main smokes already drained; `opencode-validator-live.mjs` now does too. (The policy refusal above was proven AFTER this fix — it is the remaining, provider-side cause.)

**Remediation path (user decision — involves provider/account choice):** run the validator leg against a provider/model that permits tool-disabled requests (the script accepts an explicit `[model]` argument), or obtain a non-free-tier key for the same host. Removing the tools map is NOT an option: it would weaken the frozen §8/§9 structural isolation. No product change is warranted.

**Required evidence once a permissive provider is available:** PlanID, manifest ref, ValidationReport ref + result, parser accepted, session count net-zero, model identity (§31 metadata list).
