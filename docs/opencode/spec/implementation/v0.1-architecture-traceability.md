**Status:** v0.1 Integration / Architecture Exit Review — audit artifact (no production code changed)
**Baseline:** `docs/opencode/spec/opencode-ultra-plan-architecture.md` (frozen, unmodified) + `docs/opencode/spec/opencode-ultra-plan-agent-protocol.md` v0.11 (frozen contract)
**Companion document:** `v0.1-architecture-exit-review.md` (executive disposition and analysis)
**Date:** 2026-09-26
**Code audited:** `adapters/opencode` at worktree HEAD (`git status` clean at review start; the only changes made by this review are the two audit documents)

---

## Method

1. Both frozen baseline documents were read in full; every architecture section was assigned a normative-strength class before any implementation judgment.
2. All 14 phase reports (`docs/opencode/spec/implementation/phase-*.md`) were digested as evidence leads; their highest-risk claims were then verified against actual source and tests.
3. The implementation reality was established by direct source inspection (`adapters/opencode/src` — 52 files, ~13k LOC; `test` — 22 files) across five parallel read-only audit passes: context architecture, authority/mutation paths, durable store/crash/concurrency, read surface/errors/runtime/live smokes, and phase-report cross-check.
4. Full verification was re-run with true producer exit codes (see the Exit Review §Verification Results).
5. Every requirement below received exactly one primary disposition from the frozen vocabulary (`PASS`, `PASS_WITH_INTERPRETATION`, `DEFERRED_NON_BLOCKING`, `OUT_OF_SCOPE_BY_ARCHITECTURE`, `UNVERIFIED`, `RELEASE_BLOCKER`) and the strongest available evidence level (`S` source, `T` deterministic test, `C` crash/concurrency process proof, `L` real OpenCode live-runtime proof).

Citations are `file:line` inside `adapters/opencode/` unless prefixed `repo:`.

## Normative-strength Rules

| Class | Assignment rule used |
|---|---|
| MUST / invariant | Stated in architecture §35, or phrased as an absolute property ("only", "never", "must", "always") that a Core Invariant depends on |
| Required v0.1 behavior | Normatively worded behavior not excluded by §36 and not carved out of v0.1 by an explicit "v0.1 does not require" enumeration (§13's four RAG items are the only such enumeration in the context architecture) |
| SHOULD / MAY / optional | Explicit permissive wording ("may", "should", "can", "example") |
| NON-GOAL | Listed in §36 |
| DESCRIPTIVE | Illustrative diagrams/examples ("Example:", module-layout suggestions, §2/§4.1/§6/§11 diagrams, §37 layout) |

Sections specifically re-classified by wording (Exit-Review brief §7): §14 L1's YAML block is introduced by "Example:" (the layer requirement is "logically separated run state", not the exact fields); §15 "support projection levels **such as**" (levels are the design vocabulary of the §13 pipeline); §19 "every context assembly **may** generate" (explicit MAY); §23 evidence kinds "**may** include"; §37 "**A likely** implementation layout" (DESCRIPTIVE).

## Release Blockers

Blocker rule applied: Exit-Review brief §68 (frozen-invariant violation / authority-boundary removal / unauthorized committed mutation / weakened authorization / stale design into FinalPlan / broken compaction-independence / broken same-session handoff / **omitted required component whose semantics are necessary to a frozen invariant**). Severity is independent of implementation size.

### B-A — Conflict resolution lifecycle is unimplemented (architecture §7, §33)

- **Finding:** `Conflict` is a frozen first-class artifact with `status: open | "resolved"` and `resolution {action: revise_proposal | amend_decision | amend_architecture}` (arch §7). The implementation can raise conflicts (`controller.ts:1505`; model chooses `severity: "blocking"`, `registry.ts:189`) but **no code path in any stage ever transitions a conflict to `resolved`**: the closed change vocabulary contains no conflict kind, and the only `.status = "resolved"` write in the store is for questions (`store.ts:3269`).
- **Proof:** §68-condition 8 — the resolution component is necessary for the §33 precondition `blockingConflicts == 0` to be *satisfiable*; the finalization gate blocks on any open blocking conflict (`finalization/gate.ts:243-246`), and open blocking conflicts additionally **block any intersecting commit** with `conflict_blocking` (`store.ts:2884-2902`). A run-global blocking conflict (empty refs) raised in detail blocks every subsequent commit, permanently.
- **Smallest remediation boundary:** a closed `resolve_conflict` change (Proposal → user Approval → PlanCommit) plus the capability decision for synthesis substates.

### B-B — Model-raised blockers in synthesis have no sanctioned cure (architecture §33, §9, §4.1)

- **Finding:** `record_question` (model controls `blocking`, `registry.ts:124`) and `raise_conflict` are granted in **all seven synthesis substates**; the finalization gate blocks on them. The only cure for a blocking question is `resolve_question` inside a Proposal — but `prepare_proposal` is withheld in synthesis (architecture/detail only), and the only synthesis→detail exit (`request_reopen`) requires a findings report. A blocking question raised in a validation-clean / final-candidate-ready / final-proposal-ready run therefore makes §33's `blockingQuestions == 0` permanently unreachable.
- **Aggravator:** no abort path exists (`transitionLifecycle` has zero callers; `aborted` unwritable), and the one-active-run invariant means the wedged session cannot start a new run.
- **Proof:** same §68-condition 8 form as B-A (precondition satisfiability); deterministic reachability shown by the capability matrix itself (protocol v0.11 §4).
- **Smallest remediation boundary:** a narrow resolution-only proposal authority in synthesis substates, or a sanctioned withdraw/abort workflow — either restores satisfiability of §33.

### B-C — Architecture-level design remediation has no legal path (architecture §7, §8, §9.1, Invariant 12)

- **Finding:** Section and decision reopen are fully implemented, but an approved **Architecture** can never be changed: no `amend_architecture` change kind exists (frozen §7 names it as a conflict resolution action; §9.1's amendment type admits `ArchitectureRef` scope), `add_architecture` is initial-only, and architecture-scope validation findings are refused section reopen (`reopen_target_unsupported`, protocol §7.12) and stay blocking.
- **Consequence:** an architecture-scope semantic finding (or architecture-scoped blocking conflict) leaves the run permanently un-finalizable — the exact "architecture-level finding with no legal correction path" case the Exit-Review brief §74 flags as a potential real blocker. Confirmed real: all design-remediation cases are NOT satisfiable through Section reopen alone.
- **Proof:** §68-condition 8 (Invariant 12's amendment mechanism + §33 satisfiability).
- **Smallest remediation boundary:** `amend_architecture` change + architecture reopen admission (mirroring the section-reopen machinery), or a documented architecture finding→new-run escape hatch with a sanctioned abort.

### B-D — The frozen Context Architecture (§§13–16, §28-retrieval) is not implemented (architecture §13–16, §28; Invariants 21/23 substrate)

- **Finding:** Only the Renderer-for-L0/L5 exists (`context/protocol.ts` via `experimental.chat.system.transform`, `index.ts:107-215`). Structural Retrieval, Context Projection (identity/summary/relevant/full + dependency defaults), the Budget Manager (P0–P3), L2 automatic supply (goal / hard constraints / compact architecture — "Always includes"), L3 content supply (decisions, interfaces, question/conflict content, downstream impact), and §28's evidence retrieval priorities have **no implementation** (`src/context/` = protocol.ts + a never-instantiated trace.ts; tree-wide grep: zero budget/priority/token-estimation code).
- **Why blocker-class:** §13's only v0.1 exclusions are "embeddings; vector databases; semantic reranking; custom repository indexes" — by explicit enumeration the remainder of the context architecture is in v0.1 scope; §14 requires every planning inference to receive the layers. The deferrals recorded in phase reports (2E1 §45, 2E2 §49) and the protocol doc's "later phases" notes are implementation-layer records; the frozen architecture contains no such deferral, and the audit-only rule forbids treating protocol wording as an architecture amendment.
- **What survives:** L0, L1 (orientation line + stage guidance), L4-as-principle, L5 (full checklist + server-side authorization), stable projections (§17), and deterministic per-tool renders — necessary but, per Exit-Review brief §31, not sufficient.
- **Smallest remediation boundary:** one Context Architecture phase implementing the §§13–16 pipeline over the existing store (retrieval → projection → budget → render), plus §28 evidence retrieval priorities and a ContextTrace-or-equivalent observability record; exit tests per layer (injection, budget priority ordering, P0 preservation, trace reasons) plus a live compaction/reconstruction proof.
