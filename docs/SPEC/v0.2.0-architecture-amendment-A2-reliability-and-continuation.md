## 0. Executive Summary & Purpose

Phase Plan v0.2.0 established a rigorous deterministic state machine, cryptographic audit trails, and strict capability gates for supervised multi-stage execution. However, operational evaluation in large-scale multi-stage engineering projects revealed seven execution reliability gaps (P1 through P7):

1. **P1 (All-or-Nothing Replan)**: Terminal `replan_required` discarded completed stage achievements upon local interface changes.
2. **P2 (Shell Capability Diode)**: An over-strict gate forced either disabling the shell or granting all high-risk capabilities (git push, network, dependency mutation).
3. **P3 (Supervisor Long-Horizon Context Drift)**: Bounded recency (`SUPERVISOR_CONTEXT_RECENT_LIMIT = 10`) truncated early invariants and cross-stage contracts.
4. **P4 (Model Transaction Bookkeeping Burden)**: The model was forced to copy-paste mechanical SHA256 hashes (`objectiveHash`, `contentHash`) and candidate revisions.
5. **P5 (Indeterminate Attempt Deadlock)**: Crash recovery fences blocked recovery inspection operations, with no tiered process timeouts.
6. **P6 (Formal Verifier Independence Quality)**: Verifiers merely re-ran happy-path executor tests instead of independently seeking falsification counterexamples.
7. **P7 (Abort Workspace Dirty Residue)**: Terminal abort left unaccepted and temporary files mixed with user modifications without an Abort Manifest or safe cleanup options.

This amendment formally records the architectural modifications that resolve these seven problems while strictly preserving all core architectural invariants.

---

## 1. Non-Negotiable Invariants Preserved

1. **FinalPlan Immutability**: The user-approved FinalPlan is an immutable normative execution contract. Neither Supervisor nor Worker may mutate it in flight.
2. **ExecutionRun Permanent Binding**: Each ExecutionRun remains permanently bound to its exact FinalPlan version. Predecessor runs are never rebound.
3. **Domain Separation**: Plan Memory, Execution Memory, and physical Workspace remain strictly separated.
4. **ExecutionCommit Monopole**: `ExecutionCommit` remains the sole object authorized to advance `acceptedHead` (distinct from Git commits).
5. **Worker Authority Boundary**: Workers cannot make autonomous architectural or normative interface decisions.
6. **Deterministic Core Governance**: Core remains the sole authority for state transitions, capability envelopes, optimistic locks, and gates.
7. **No Blind Re-execution**: Interrupted or indeterminate side effects are never blindly repeated.
8. **No Permission Evasion**: Tests cannot pass by removing checks, relaxing gates, or ignoring failures.
9. **No Text-as-Truth**: Natural language summaries and model outputs are not automatically approved design facts.
10. **Non-Destructive Workspace Policy**: No unauthorized destructive git operations (`git reset --hard`, `git clean -fd`) are executed against real user repositories.

## 2. Problem-by-Problem Architecture Amendments

### 2.1 P1: Incremental Replan & Execution Continuation

- **Old Constraint**: When `ExecutionRun.lifecycle = replan_required`, the run terminated permanently. A subsequent PlanningRun and ExecutionRun had to decompose and execute all stages from scratch (ordinal 1, all pending), losing previously accepted work.
- **New Constraint**:
  - Replan requests are strictly guarded: ordinary test failures, compiler errors, or file path changes are refused (`REPLAN_REQUEST_INVALID`). Only genuine normative design gaps (unimplementable, ambiguous, or conflicting specifications) qualify.
  - Successor PlanningRuns adopt the replan issue and reopen only the affected normative scope (`needs_review`), while unaffected sections are `inherited_completed`.
  - When the successor ExecutionRun materializes, `determineContinuationReuseInTx` evaluates predecessor achievements against **Workspace Reality** (deliverable files exist on disk) and **Dependency Contracts** (prerequisite steps satisfied).
  - Eligible stages are marked `completed` backed by their historical `ExecutionCommit`.
  - The latest valid reused commit becomes the seeded `accepted_head_commit_id` for the new run.
  - The new run activates the first pending stage and opens its verification window rooted in the seeded accepted head.
- **Rationale**: Eliminates the all-or-nothing replan penalty while strictly keeping predecessor runs immutable.
- **Compatibility**: Predecessor ExecutionRun and FinalPlan remain byte-identical; all existing handoff and approval tests pass unchanged.

### 2.2 P2: Layered Capability Enforcement

- **Old Constraint**: `commandExecution = true` paired with any `false` in `networkAccess`, `dependencyMutation`, `gitCommit`, `gitPush`, `externalServiceMutation` refused to launch with `CAPABILITY_ENFORCEMENT_UNAVAILABLE`.
- **New Constraint**:
  - Distinguishes mechanical tool boundaries (`repositoryRead`, `repositoryWrite`, `commandExecution`), execution boundary checks on shell commands (`git push`, `git commit`, `curl`, `npm install`), and audited semantic constraints.
  - Introduces `enforcementPolicy = 'layered'` allowing `commandExecution = true` with fine-grained restrictions.
  - The PreToolUse hook inspects Bash/PowerShell tool inputs at the execution boundary: attempts to run restricted operations (`git push`, `git commit`, network calls) are denied with `CAPABILITY_DENIED`.
  - System exposes `capabilityEnforceabilityReport` explicitly distinguishing `enforceable` vs `advisory` mechanisms without false sandbox claims.
  - Legacy callers without layered policy retain strict fail-closed behavior for backward compatibility.
- **Rationale**: Enables local build and testing without exposing repositories to unauthorized remote pushes or network exfiltration.

### 2.3 P3: Execution Evolution Ledger (L0 / L1 / L2 Context)

- **Old Constraint**: Bounded recency (`SUPERVISOR_CONTEXT_RECENT_LIMIT = 10`) truncated history, causing supervisors in multi-stage runs to lose early invariants and cross-stage findings.
- **New Constraint**:
  - Introduces structured three-layer context:
    - **L0 (Normative Context)**: Hard constraints, goals, architecture decisions, and section contracts from the approved FinalPlan.
    - **L1 (Execution Evolution Context)**: All completed stages, cross-stage contracts, engineering discoveries, unresolved risks, and superseded assumptions with explicit validity status derived from accepted `ExecutionCommits`.
    - **L2 (Recent Working Context)**: Bounded recency window (last 10 items) for current window directives, attempts, reports, and assessments.
  - Context is deterministically reconstructible from the Store across compactions and session restarts.
- **Rationale**: Prevents long-horizon context drift in multi-stage projects while remaining within token budgets.

### 2.4 P4: Model-Facing MCP Contract Simplification & Assessment Tokens

- **Old Constraint**: The supervisor model was forced to copy-paste mechanical SHA256 hashes (`objectiveHash`, `contentHash`, `finalPlanHash`) and candidate revisions in `submit_supervisor_assessment`.
- **New Constraint**:
  - Core provides `get_execution_acceptance_context` issuing a signed `assessment_token` binding `executionRunId`, `windowId`, and `candidateRevision`.
  - Core automatically derives deterministic obligations (`stageObjectiveObligation` or `executionRunCompletionObligation`) when `covered_obligations` is omitted.
  - Optimistic concurrency is strictly enforced: if candidate revision advances before submission, the token is rejected with `SUPERVISOR_ASSESSMENT_STALE`.
  - Supervisor is responsible solely for semantic judgments (`supporting`, `superseded`, `blocking`).
  - Idempotent retry convergence is supported: duplicate submissions return the existing commit without duplicating rows.

### 2.5 P5: Recovery Capability Boundary & Tiered Timeouts

- **Old Constraint**: An indeterminate attempt blocked execution via `requireNoUnresolvedIndeterminateFenceInTx` without tiered timeouts, and process crashes could cause deadlocks.
- **New Constraint**:
  - Tiered timeouts: startup timeout (30s), no-progress heartbeat timeout (60s), and absolute execution limit (300s).
  - Process liveness fence: an attempt cannot be marked indeterminate while a child subprocess is still running. Fails closed with `WORKER_PROCESS_STILL_ALIVE` until the process is verified terminated.
  - Recovery Capability Boundary: recovery operations (`get_attempt_recovery_context`, `issue_attempt_reconciliation`, `resolve_indeterminate_attempt`, `request_execution_replan`) remain accessible while ordinary execution is fenced.
  - Late/delayed report submissions converge idempotently without error.
  - Repeated resolution calls converge idempotently on the durable resolution without secondary revision advance.

### 2.6 P6: Formal Verifier Adversarial Quality & Invariant Falsification

- **Old Constraint**: Verifiers ran in separate sessions but often merely repeated executor happy-path tests, risking rubber-stamping regression defects.
- **New Constraint**:
  - Verifiers are tasked with adversarial falsification: independently seeking counterexamples and checking cross-component invariants.
  - Negative verifier findings (e.g. invariant violations) must be reported as `failed` or `blocked`.
  - If a blocking verifier report exists, the acceptance gate strictly rejects the commit (`ACCEPTANCE_BLOCKED`).
  - Supervisor triggers `rework`, executor fixes the defect, and a fresh verifier must pass before acceptance is permitted.
  - Pure mechanical changes (e.g. documentation formatting) are accepted with clean static/build checks without forcing unnecessary test files.

### 2.7 P7: Workspace Lifecycle & Abort Reconciliation

- **Old Constraint**: Terminal abort halted execution but left dirty files, unaccepted modifications, and temporary artifacts unmanaged in the workspace.
- **New Constraint**:
  - Captures physical execution baseline (git HEAD, branch, pre-existing modified/untracked files and fingerprints).
  - Generates comprehensive `AbortManifest` categorizing:
    - Accepted files (from completed ExecutionCommits).
    - Unaccepted candidate files (from uncommitted attempts).
    - User pre-existing files (guaranteed never deleted).
    - Temporary build artifacts.
  - Non-destructive default: abort performs NO automatic file deletion or git resets.
  - Explicit safe cleanup (`clean_unaccepted_only`): user-authorized operation that safely deletes only unaccepted candidate files and temporary files, strictly preserving user pre-existing files and accepted deliverables.

## 4. Migration & Compatibility Plan

- **Schema Migration**: Unchanged at schema version 26. All new metadata fields (continuation lineage, physical baselines, evolution ledgers, assessment tokens) use existing JSON/text columns (`planning_baseline_json`, `execution_start_baseline_json`, `detail_json`).
- **Backward Compatibility**:
  - Legacy verbose assessment calls with explicit `covered_obligations` and `expected_candidate_revision` remain fully supported.
  - Legacy capability envelopes without `enforcementPolicy = 'layered'` continue to fail closed with `CAPABILITY_ENFORCEMENT_UNAVAILABLE`.
  - Replan and continuation operate additively without mutating or corrupting historical execution runs.
- **Rollback Safety**: Any database created under this amendment opens and operates cleanly on earlier v0.2.0 runtimes without schema corruption.
